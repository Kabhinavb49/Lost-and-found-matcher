# 400-word Reflection

L&F MATCH addresses a practical campus problem: lost-property reports and found-item records can accumulate faster than staff can compare them manually. The project combines a language model with ordinary Python so that each technology has a clearly defined responsibility. Gemini reads one report at a time and extracts a small set of fields. Python checks the extracted facts, compares records, applies the scoring rules and creates the output files. This separation makes the result easier to test and explain than asking an AI model to decide every possible match.

One important learning was that an AI response should not be trusted automatically. A model may return valid-looking JSON while including a brand, colour or location that was never written in the report. L&F MATCH therefore checks extracted values against the original text and changes unsupported colour, brand and place values to null. The fallback also helps the program continue when the API is unavailable, although fallback results are deliberately conservative and may be less informative.

The scoring rules make the matching process transparent. Matching colour and brand each add two points, while matching place adds one point. A different item category, a colour or brand conflict, an item category of “other”, or a date gap greater than 30 days prevents an automatic suggestion. The evaluation harness checks likely, possible and no-match cases. Red-team tests examine vague reports, unsupported brand guesses and instructions embedded in report text.

The project also demonstrates why a technical result should not replace human judgment. Two people may describe similar objects, and even a high score cannot establish ownership. A found item suggested for more than one lost report is flagged for additional review. Before handing over an item, the help desk must ask the claimant for a detail that does not appear in either report and verify the answer.

If I extend this project, I would add a staff interface, better handling of spelling variations, configurable campus locations and a larger labelled evaluation dataset. I would also measure false positives and false negatives using real, anonymized examples approved for this purpose. Any extension would preserve the central rule: the tool recommends candidates, while a human verifies ownership. Building L&F MATCH improved my understanding of CSV processing, functions, dictionaries, nested loops, sorting, dates, API calls, validation, testing, exception handling and responsible AI design.
